## 2. Мінімум синтаксису, який треба впізнавати

У `.jsx` файлі компонент — звичайна JavaScript-функція, назва якої починається з великої літери. Вона повертає JSX: розмітку, схожу на HTML. `App.jsx` містить логіку й розмітку, а загальний CSS лежить у `styles.css`. У `main.jsx` виклик `createRoot(...).render(<App />)` монтує компонент у `<div id="app">` з `index.html`.

```jsx
import { useState } from 'react'

function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(count + 1)}>Počet: {count}</button>
}
```

`useState(0)` дає пару: поточне значення `count` і функцію `setCount`, яка його змінює. Після `setCount` React викликає компонент знову й показує нове значення. `const` оголошує змінні всередині **одного** виклику компонента; саму `count` не переприсвоювати. `useState` викликати тільки на верхньому рівні компонента, а не в `if`, циклі чи обробнику події. `() => ...` — коротка функція, яку викличуть після кліку, а не під час малювання кнопки.

```jsx
<>
  <form onSubmit={loadTodos}>
    <input value={name} onChange={(event) => setName(event.target.value)} />
    <button type="submit">Načítať</button>
  </form>
  {error && <p role="alert">{error}</p>}
  <ul>{todos.map((todo) => <li key={todo.id}>{todo.title}</li>)}</ul>
</>
```

У JSX JavaScript-вираз пишуть у `{...}`. `value` задає значення поля, а `onChange` записує новий текст у стан: разом це **кероване поле**. `onSubmit` отримує функцію, коли форму надсилають кнопкою або клавішею Enter. `error && ...` показує абзац, лише якщо помилка непорожня. `map` перетворює масив на список елементів; `key` має бути стабільним ID задачі. `{todo.title}` показує текст і **не трактує його як HTML**. Не використовувати `dangerouslySetInnerHTML` для даних із API.

JSX має відмінності від HTML: писати `className`, а не `class`; `htmlFor`, а не `for`; закривати одиночні теги (`<input />`). Один компонент повертає один кореневий елемент або фрагмент `<>...</>`. У JSX `onSubmit={handleSubmit}` викликає функцію, а у ній потрібен `event.preventDefault()`, щоб браузер не перезавантажив сторінку.

```js
const unfinished = todos.filter((todo) => !todo.is_finished)
```

`filter` повертає новий масив, не змінюючи `todos`. `=>` — короткий запис функції, `!` означає «не». Для максимум 50 задач достатньо обчислювати відфільтрований масив під час рендеру. `useMemo` тут поки не потрібен. Крапка в `todo.title` означає «візьми поле `title` об'єкта `todo`». Масив об'єктів виглядає так: `[{ id: 1, title: 'Úloha' }]`.

```js
async function load() {
  try {
    const result = await getTodos(name)
    setTodos(result)
  } catch (error) {
    setError('Úlohy sa nepodarilo načítať.')
  }
}
```

`async` дозволяє чекати на мережу через `await`, не блокуючи браузер. `try` — спроба; `catch` — дія при помилці. `setTodos(result)` оновлює стан React. Після `await` код продовжиться, коли прийде відповідь або помилка. Масив для локального додавання створювали б так: `setTodos((previous) => [...previous, newTodo])`; але після запису на сервер у цьому завданні краще заново отримати його актуальні дані.

**Міні-вправи:** (1) додати лічильник отриманих задач у заголовок; (2) зробити різний текст для завершеної та незавершеної задачі; (3) пояснити, яку роль мають `name` і `setName` та чому не можна писати `name = 'нове'`.

## 3. Зрозуміти API перед створенням кнопок

Відкрити <https://wt1zadanie.iolab.sk/docs> і розгорнути кожен метод. API — чужа програма, з якою мій сайт говорить через HTTP. URL має вигляд `https://wt1zadanie.iolab.sk/api/{name}`; `{name}` — **мій дозволений ідентифікатор**, а не довільний тестовий рядок. Сервер приймає лише імена зі свого списку; неправильне ім'я може дати HTTP 403. Не вгадувати і не перебирати чужі ідентифікатори. У стартовому екрані ідентифікатор вводиться вручну, що умова дозволяє.

**Мій підтверджений ID для API — `xpostaichuk`.** Це мій шкільський логін, який є в адресі шкільного сервера для Z1. Перевірка `GET https://wt1zadanie.iolab.sk/api/xpostaichuk` 07.11.2026 дала HTTP 200 і п'ять стартових задач. У полі на початковому екрані Z3 вводити саме `xpostaichuk`, без `~`, домену чи повної URL. Числові `id` окремих задач брати з поточної відповіді сервера, а не запам'ятовувати назавжди.

**Локальний доступ і CORS:** у `vite.config.js` є проксі `/api` → шкільний сервер. Тому під час `npm run dev` браузер звертається до свого локального Vite, а Vite передає запит API. У зібраній версії Vite-сервера вже немає: код використовує пряму URL API. Станом на 07.11.2026 API не повертав заголовок `Access-Control-Allow-Origin` і не приймав CORS-preflight; перевірити це з викладачем або адміністраторами до публікації на шкільному сервері. Однією лише зміною React-коду дозвіл CORS на чужому сервері не додати.

Важливо: перший `GET /api/{name}` **створює список і п'ять прикладів**. Тому навіть перевірка читання впливає на сервер. На одного студента дозволено максимум **50 задач**; спроба створити понад межу може скинути список до п'яти прикладів. Для навчальних проб не накопичувати десятки задач і перед `reset` пам'ятати, що він видаляє власні поточні дані.

| Операція | Метод і шлях | Що очікувати |
| --- | --- | --- |
| Усі задачі | `GET /api/{name}` | Об'єкт студента; задачі всередині `todos` |
| Одна задача | `GET /api/{name}/{todo_id}` | Об'єкт задачі |
| Створення | `POST /api/{name}` | JSON `TodoCreate`, успіх HTTP 201 |
| Заміна задачі | `PUT /api/{name}/{todo_id}` | **Усі поля** `TodoCreate`, успіх HTTP 200 |
| Видалення | `DELETE /api/{name}/{todo_id}` | Успіх HTTP 204, **тіла JSON немає** |
| Завершити | `PATCH /api/{name}/{todo_id}/done` | Повертає оновлену задачу |
| Знову відкрити | `PATCH /api/{name}/{todo_id}/undone` | Повертає оновлену задачу |
| Відновити приклади | `POST /api/{name}/reset` | Заміна всього списку на 5 задач |

`TodoCreate`: `title` — обов'язковий текст до 200 символів; `description` — необов'язковий до 1000; `date_from` і `date_to` — обов'язкові дати й час у ISO 8601; `is_finished` — `true`/`false` (за замовчуванням `false`, але для `PUT` передавати явно). У відповіді задачі додатково є `id`, `student_id`, `created_at`. `GET /api/{name}` повертає **об'єкт** на кшталт `{ id, name, created_at, todos: [...] }`, а не сам масив. Саме тому в `getTodos()` є `return student.todos`.

У `todosApi.js` уже видно основний запит:

```js
const url = `${API_BASE}/${encodeURIComponent(name)}`
const response = await fetch(url)
if (!response.ok) throw new Error(`HTTP ${response.status}`)
const student = await response.json()
return student.todos
```

Зворотні лапки створюють рядок із підстановкою `${...}`. `encodeURIComponent(name)` правильно кодує частину URL. `fetch` **не кидає помилку тільки через 4xx/5xx**, тому перевірка `response.ok` обов'язкова. `response.json()` читає JSON-відповідь. Мережева помилка, навпаки, потрапляє в `catch`.

**Перевірка:** відкрити DevTools → Network, завантажити свій список і знайти GET-запит, статус та JSON. Якщо сервер повернув 403, перевірити ідентифікатор. Не переходити до форм, поки не можу пояснити відповідь GET.

## 4. Зробити один стан даних для списку і календаря

Тримати один стан `const [todos, setTodos] = useState([])` у `App.jsx`. І список, і календар отримують дані з нього. Не створювати другий незалежний масив задач для календаря. `name` — текст, який зараз введено у формі; `activeName` — ID списку, який **успішно** завантажено. Для майбутніх POST/PUT/DELETE/PATCH використовувати `activeName`, щоб випадкова зміна поля вводу не спрямувала запис в інший список. Після успішного запису викликати функцію повторного GET; так обидва види одразу отримають стан сервера. У поточній базі `loadTodos(event)` є обробником форми й очікує `event`. Перш ніж викликати завантаження після інших операцій, **відокремити** сам GET у функцію на кшталт `refreshTodos(studentName)`, а обробник форми нехай викликає її після `event.preventDefault()`. Інакше `loadTodos()` без аргументу впаде на `event.preventDefault()`. Якщо операція неуспішна — залишити старий список і форму з введеними значеннями, показати помилку.

Коли `App.jsx` стане завеликим, винести видимі частини в `src/components/TodoList.jsx`, `TodoForm.jsx`, `TodoCalendar.jsx`, `TodoDetails.jsx` та `StatusMessage.jsx` **по одній**, коли відповідний функціонал уже працює. Не потрібно створювати порожні компоненти заради структури. `App.jsx` передає дані та функції як props: `<TodoList todos={todos} onEdit={startEditing} />`. Усередині `TodoList` це звичайні аргументи: `function TodoList({ todos, onEdit }) { ... }`. Після кліку дочірній компонент викликає `onEdit(todo)`, а `App.jsx` вирішує, яку API-функцію викликати. Так дані йдуть униз, а повідомлення про дію — через callback угору.

Приклади стану, який знадобиться: `loading`, `saving`, `error`, `successMessage`, `selectedTodo`, `formOpen`, `statusFilter`, `searchText`, `sortField`. Для кожного обраного стану створити `useState`. `loading` — для GET, `saving` — для запису. Кнопка надсилання має бути `disabled={saving}`, щоб подвійний клік не створив дубль. Не зберігати у стані те, що легко обчислити з `todos`, наприклад кількість задач.

## 5. Додати створення задачі (POST)

1. Намалювати форму з полями `title`, `description`, `date_from`, `date_to`; підписи словацькою (`Názov`, `Popis`, `Začiatok`, `Koniec`). Для часу зручно взяти `<input type="datetime-local">`.
2. Зробити керовані поля: `value={form.title}` та `onChange={(event) => setForm((previous) => ({ ...previous, title: event.target.value }))}`. `...previous` копіює старі поля об'єкта, а `title` замінює одне поле. Можна почати з окремих `useState` для кожного поля, якщо так легше зрозуміти. Не змінювати `form.title = ...` напряму: React тоді не отримає оновлення стану. На початку форма може бути в `App.jsx`, потім винести у `TodoForm.jsx`.
3. При натисканні `Uložiť` прибрати пробіли навколо назви через `.trim()`. Перевірити: не порожня; довжина ≤ 200; опис ≤ 1000; обидві дати присутні; `new Date(date_from) <= new Date(date_to)`. Помилки показувати біля **відповідних** полів, а не лише загальним повідомленням.
4. Перетворити локальний час форми у формат для API. Приклад: `new Date(form.date_from).toISOString()` дає UTC-рядок ISO 8601. Спершу переконатися, що дата валідна (`Number.isNaN(date.getTime())` — помилка). Не додавати вручну `Z` до місцевого часу.
5. Створити в `todosApi.js` функцію `createTodo(name, payload)` із `fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(payload) })`.
6. Перевірити `response.ok`; лише після успіху закрити/очистити форму, показати підтвердження й повторно викликати GET. При помилці зберегти введення, дати повторити.

Приклад **форми JSON** (це лише зразок даних, не треба надсилати його без потреби):

```json
{
  "title": "Pripraviť prezentáciu",
  "description": "Skontrolovať posledný slajd",
  "date_from": "2026-11-12T14:00:00.000Z",
  "date_to": "2026-11-12T15:00:00.000Z",
  "is_finished": false

```

**Перевірити:** порожню назву, 201 символ, 1001 символ опису, кінець раніше початку, нормальне створення, подвійний клік, відсутній інтернет. Після оновлення сторінки задача повинна лишитися на сервері.

## 6. Редагування, видалення й стан задач

**Редагування (PUT):** після натискання `Upraviť` відкрити **ту саму** форму, заповнити поточними полями задачі. Для `datetime-local` треба місцевий формат `YYYY-MM-DDTHH:mm`. Не застосовувати `toISOString().slice(0, 16)` для заповнення такого поля: це UTC і може зсунути показаний час. Зробити маленьку функцію, що бере `new Date(iso)` та її місцеві `getFullYear()`, `getMonth() + 1`, `getDate()`, `getHours()`, `getMinutes()`; двозначні частини отримати через `String(number).padStart(2, '0')`. При PUT надіслати `title`, `description`, `date_from`, `date_to`, `is_finished`, навіть якщо змінилося одне поле. `PUT` замінює всю задачу.

**Видалення (DELETE):** показати підтвердження з назвою задачі (`window.confirm` — найпростіший робочий початок; пізніше можна власний доступний діалог). Лише після згоди викликати API. Для HTTP 204 **не** викликати `response.json()` — відповідь порожня. Після успіху повторно завантажити дані. При скасуванні запит не надсилати.

**Завершення / повторне відкриття (PATCH):** з `is_finished === false` викликати `/done`, з `true` — `/undone`. PATCH тут не потребує JSON-тіла. Після успіху перечитати список. Підпис кнопки має відповідати поточному стану: `Dokončiť` / `Znovu otvoriť`.

**Reset:** кнопка `Obnoviť ukážkové úlohy` з окремим попередженням, що поточні задачі зникнуть і будуть замінені п'ятьма прикладами. Запит `POST /api/{name}/reset` тільки після підтвердження. Потім GET. Не перевіряти цю дію на даних, які хочу зберегти.

Порядок роботи: спершу завершити і вручну перевірити POST, тоді PUT, DELETE, PATCH, reset. Кожен новий метод писати в `todosApi.js`; `App.jsx` не повинен містити URL і налаштування HTTP. Не додавати кнопку, яка нічого не робить.

## 7. Список: пошук, фільтр і порядок

Залишити `todos` як оригінальні серверні дані. Під час рендеру обчислити `visibleTodos`: (1) фільтр `všetky / nedokončené / dokončené`; (2) пошук у `title` через `toLocaleLowerCase('sk-SK').includes(...)`; (3) сортування копії масиву `[...result].sort(...)` за `date_from` або `date_to`. Не викликати `todos.sort(...)` на оригінальному стані: `sort` змінює масив на місці, а стан React треба берегти від мутацій. Календар має отримати повну колекцію; фільтр списку не повинен видаляти з неї задачі. При максимумі 50 задач не потрібна окрема бібліотека стану чи оптимізація `useMemo`.

Мінімум у кожному рядку: назва, початок/кінець, стан, `Upraviť`, `Odstrániť`, `Dokončiť` або `Znovu otvoriť`. Можна показати опис у розгорнутій частині. Прострочена задача: `!todo.is_finished && new Date(todo.date_to) < new Date()`; її відрізнити текстом/іконкою/кольором. Колір сам по собі не повинен бути єдиним знаком статусу. Для порожнього списку й порожнього результату фільтра — **різні** зрозумілі повідомлення.

**Перевірити:** пошук без урахування великих літер, зміну фільтра після PATCH, сортування за обома датами, пустий результат, задачу з однаковим початком/кінцем, задачу після дедлайну.

## 8. Календар (FullCalendar)

Пакети FullCalendar **v6.1.22** уже додані в `package.json`. Не копіювати приклади v7 без адаптації: у v7 змінилися імпорти й CSS. Користуватися документацією [React-компонента v6](https://legacy.fullcalendar.io/v6/react). У `TodoCalendar.jsx` імпортувати `FullCalendar` з `@fullcalendar/react`, а `dayGridPlugin`, `timeGridPlugin`, `interactionPlugin` — з відповідних `@fullcalendar/...` пакетів. `dayGrid` дає місяць, `timeGrid` — тиждень/день із часом, `interaction` — клік/виділення інтервалу.

У React параметри календаря передаються як props компонента: `<FullCalendar plugins={[dayGridPlugin, timeGridPlugin, interactionPlugin]} initialView="dayGridMonth" ... />`. Знадобляться `headerToolbar` з `prev,next today` і `dayGridMonth,timeGridWeek,timeGridDay`, `selectable={true}`, `events={events}`, `eventClick={handleEventClick}`, `dateClick` або `select`. Для словацької локалі імпортувати `skLocale` з `@fullcalendar/core/locales/sk` і передати `locale={skLocale}`. Спочатку показати календар без подій, перевірити перемикання трьох видів і навігацію, потім підключати реальні задачі.

Перетворювати задачі на події **лише як похідні дані**:

```js
const events = todos.map((todo) => ({
  id: String(todo.id),
  title: todo.title,
  start: todo.date_from,
  end: todo.date_to,
  extendedProps: { is_finished: todo.is_finished },
}))
```

Цей фрагмент показує мапування, але сам собою не створює календар. `map` створює новий масив; `id` допомагає знайти оригінальну задачу. Передати масив як `events={events}`. Для стану додати класи подій і видимий підпис/ознаку, щоб завершені й активні відрізнялися не лише кольором. У `eventClick` знайти задачу по `id` і відкрити деталі з діями. Для вибору дати/часу (`dateClick`/`select`) відкрити форму з наперед заповненими датами. FullCalendar не повинен окремо зберігати задачі: після `setTodos` React знову передасть актуальні `events`.

**Пастка:** у FullCalendar кінець виділеного `select` інтервалу є **невключним** (`exclusive`). Якщо виділити цілий день, `end` може бути початком наступного дня. Не записувати це сліпо як час закінчення задачі; для вибору одного дня запропонувати розумний годинний інтервал, а для довгого інтервалу явно показати користувачеві фактичні часи у формі. Задача на кілька днів повинна мати реальні `start` і `end`; перевірити її в усіх трьох видах.

**Перевірити:** місяць/тиждень/день, `predchádzajúce / nasledujúce / dnes`, задачу через північ, завершену задачу, клік по події, вибір часу для нової задачі, автоматичне оновлення після PUT/PATCH/DELETE. На мобільному календар може потребувати вужчої панелі/меншого toolbar, але горизонтального переповнення бути не повинно.

## 9. Помилки, час і доступність

Стан запиту: показувати `Načítavam…` або `Ukladám…`; на час POST/PUT вимикати повторне надсилання. Після успіху — коротке словацьке повідомлення, після помилки — зрозуміла причина й можливість спробувати знову. Для HTTP 422 спершу подивитися JSON з `detail`: сервер часто дає конкретне поле і причину. Для мережевої помилки сказати, що сервер недоступний; не стирати форму. Для 403 — перевірити дозволений ідентифікатор. Для 204 не парсити JSON. Не показувати сирий HTML-вміст із сервера через `dangerouslySetInnerHTML`; звичайні `{todo.title}` і `{todo.description}` безпечніше показують текст.

Час з API може мати `Z` (UTC) або часовий зсув. Для показу людині використовувати `new Date(iso).toLocaleString('sk-SK')`; це місцевий час браузера. Для відправлення з `datetime-local` зробити `new Date(localValue).toISOString()`. Перевірити на реальному прикладі, що 14:00 у формі після збереження знову показується як 14:00 локально. Не змішувати UTC-рядок із локальним рядком без перетворення. Особливо перевірити дату біля переходу на літній/зимовий час.

Мінімум доступності: `<label htmlFor="...">` для кожного поля в JSX, звичайні `<button>`, видимий фокус з клавіатури, текстові статуси, повідомлення про помилку поруч із полем, достатній контраст, не покладатися лише на колір. Діалог видалення має бути доступний клавіатурою. У `App.jsx` уже є приклад `role="alert"` для помилки та `role="status"` для завантаження.

## 10. Оформлення і мобільна версія

Спершу зробити ясний потік: вибір ідентифікатора → огляд задач → створення/дії → календар. Відразу спланувати, де на телефоні будуть перемикач списку/календаря, головна кнопка створення і фільтри. Намалювати собі два прості ескізи: широкий екран і екран телефону. Вибрати одну палітру, один шрифт основного тексту, послідовні відступи і стиль кнопок. Стартовий CSS можна змінювати; це не фінальний дизайн.

Вимоги PDF: назва, favicon, продумана шапка й підвал, секція `O projekte` з описом React, Vite, Fetch API, FullCalendar, адаптація для desktop/tablet/mobile, Chrome і Firefox, словацька мова з діакритикою, UTF-8. Не залишати декоративні або недіючі елементи керування. Текст у футері/`O projekte` має називати **фактично використані** бібліотеки. Не потрібно додавати Bootstrap чи Tailwind тільки тому, що PDF дозволяє їх: звичайного CSS тут достатньо.

## 11. Послідовність самостійної роботи

Працювати короткими завершеними кроками. Після кожного пункту зберегти зміни й руками пройти сценарій у браузері.

1. Запустити базу; зрозуміти `index.html` → `main.jsx` → `App.jsx`.
2. Ввести свій дозволений ID і прочитати GET у вкладці Network.
3. Пояснити собі `useState`, `value`/`onChange`, `onSubmit`/`preventDefault`, умовний JSX, `map`, `await`, `try/catch` на поточному коді.
4. Зробити форму + локальну валідацію без мережевого запису.
5. Підключити POST; перевірити після оновлення сторінки.
6. Повторно використати форму для PUT; особливо перевірити місцевий час і повний JSON.
7. Додати DELETE з підтвердженням, потім PATCH done/undone, потім reset.
8. Винести список і форму у компоненти, коли код став незручним.
9. Додати фільтр, пошук, сортування й позначення прострочених.
10. Додати FullCalendar і ті самі серверні задачі; потім дії через календар.
11. Поліпшити візуальний дизайн, мобільну версію, повідомлення, favicon, `O projekte`.
12. Пройти фінальну таблицю нижче, оновити README, побудувати `dist`, перевірити шкільний сервер і ZIP.

Коли застрягну, ставити собі вузьке запитання: «Що повертає цей `fetch`?», «Яке значення в `form.date_from` до перетворення?», «Який саме HTTP-статус прийшов?». Зменшувати проблему до одного запиту/поля/компонента. В DevTools дивитися `Console` і `Network`, а не вгадувати помилку.

## 12. Контроль перед здачею

| Сценарій | Як перевірити руками |
| --- | --- |
| Дозволений ID, перший GET | Бачу 5 прикладів сервера і їхні поля |
| Неправильний ID / сервер недоступний | Бачу помилку, сайт не падає |
| POST | Нова задача з'являється і лишається після перезавантаження |
| Невалідна форма | Не відправляється, помилка біля поля |
| PUT | Назва, опис, обидві дати й стан правильно зберігаються |
| DELETE | Без підтвердження нічого не видаляється; після підтвердження зникає |
| PATCH done/undone | Стан змінюється на сервері, у списку й календарі |
| Reset | Є попередження, потім рівно 5 прикладів |
| Пошук/фільтр/сортування | Усі комбінації працюють, порожній результат пояснено |
| Календар | 3 режими, навігація, клік, створення з дати/інтервалу, багатоденна задача |
| Час | Після збереження локальний час не зсунувся |
| Мобільний екран | Нічого не обрізано, горизонтального скролу немає, кнопки доступні |
| Chrome і Firefox | Основний сценарій повністю працює в обох |
| Збірка й ZIP | У корені ZIP `index.html`, `README.md`; немає `node_modules`; джерела присутні |
| Шкільний сервер | Відкрита URL працює, API-запити проходять, посилання додано до здачі |
| Обговорення з викладачем | Можу пояснити, чому React, як працює Fetch, звідки беруться дані, що робить кожен метод |

Для перевірки збірки:

```bash
npm run build
npm run preview
```

`npm run preview` перевіряє зібрану версію локально. На шкільний сервер завантажувати **вміст `dist/`**, а не `src/` замість нього. Для ZIP скласти в окрему папку вміст `dist/` (щоб `index.html` був у корені), додати оновлений `README.md` і вихідний код `src/`, `package.json`, `package-lock.json`, `vite.config.js`. Не вкладати `node_modules/`, `.git/`, цей особистий план або незакінчені нотатки. Назву ZIP уточнити через суперечність у PDF.
